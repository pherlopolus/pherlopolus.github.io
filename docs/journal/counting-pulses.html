Counting pulses before trusting the rev counter

The RPM investigation now has a better notebook.

Pulse logs from a reported steady-running test prompted a closer look at gaps in the pickup signal. Those gaps don’t establish whether sparks were missed: the pickup, input circuitry or software could also lose events.

The new v1.7 logger records raw digital edges and plots instantaneous RPM, a ten-interval average and the RPM selected for the wireless display. It also records rejected edges, estimated missing events and software delays, making it easier to see what the filtering is doing.

The display selection uses the actual reading when it falls within ±35% of the accepted average, otherwise falling back to that average. A reassuring number on screen is still an estimate during a gap.

The first capture build failed; a change to how recording memory is allocated was followed by passing automated software checks and successful compilation of the logger, sender and display firmware. Physical operation of the new logger and wireless pair still needs confirmation.

At this stage, recording stops at 60 seconds or when either buffer fills, so a capture can be substantially shorter. Separate 30/60-second recordings and continuous recording split into 30-second files were requested follow-up work; these were implemented in software on 30 October, with hardware verification pending.

We also explored a Hall sensor looking at the flywheel’s outer rim. That remains a mounting idea to test, with the target, pulse count, clearance and sensor suitability unconfirmed. The next useful comparison is an independent crank signal alongside the existing pickup.
