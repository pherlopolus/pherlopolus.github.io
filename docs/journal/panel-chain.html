October 2026 · retrospective · implementation

Passing messages down a panel chain

The message centre's latest networking experiment asks each panel to provide the next one with a path home.

Panel 1 registers with the coordinator. Panel 2 joins Panel 1, Panel 3 joins Panel 2, and so on. A message from a later panel travels back through its predecessors. The coordinator still needs to know which panel originated it, and its response has to make the return journey.

Why try a strict order?

It gives a defined route and a repeatable enrollment sequence. It also creates an obvious failure mode: losing Panel 2 would disconnect every panel further along the chain. The design does not silently skip the gap, so a disconnected route should make its message buttons unavailable.

What needs testing

The current package describes coordinator and universal panel sketches, panel identity, relay diagnostics and an enrollment procedure. The staged test starts with Panel 1, adds each panel in order, then removes an early panel and observes timeout and recovery. The documentation explicitly says the full package was not compiled or tested on the physical boards in that workspace.

Status: implementation and test plan. Delivery, acknowledgement and recovery across a real multi-panel chain remain to be verified.
